# 场景设计契约 v0.3：从物件齐全到视觉关系成立

2026-09-10。讨论稿，尚未取代 v0.2。用户已确定推进顺序：先改进 Schema，再用新结构重写场景内容，最后修改或重做场景。下面是可审看的字段修订提案；不启动场景重建、不实现校验器。

本轮已确认：先设计完整视觉组合，再展开重点单件；组合引用单件，各对象只定义一次，设计组合不要求制作时合并成一个模型。下文已落实其字段边界；其余 v0.3 细节继续作为工作草案。

后续范围更新：用户要求一批人物并可拳击互搏，原“无战斗小样”限制不再约束本轮新设计。下文增加可选人物表演字段；近身战斗是当前实例的需求，不成为每个 SceneDesign 的必填内容。

已确认互搏关系与观察方式：主角第一人称，首轮为玩家与 NPC 对打；NPC 彼此打斗不纳入本轮。镜头、手部画面与对手表演分别交接，不能把 NPC 的全身站姿图当成主角第一人称资产。

## 这轮修订依据

旧码头具备仓库、人物、石阶、设备和船，却没有充分保住参考中的错层岸线、建筑进退、近景设备与船的联系、人物尺度和生活活动。这首先是设计内容及交接问题，不能只靠贴图和灯光修补。

现有字段也没有被充分使用：多个物件重复整段比例说明、局部表面处理留空、船沿用地面/墙面接触套话；三个 View 重复相同的表现重点和物件列表。v0.3 同时修改字段语义与填写范例，不把所有缺口归因于字段数量。

实际小样最高 6.3 分衡量的是与简化布局派生目标的接近程度，不衡量与用户所选旧埠参考的设计差距。概念吸引力和实现接近程度须分别讨论。

## 契约数量与边界

| 契约 | 负责的决定 | 不在这里决定 |
| --- | --- | --- |
| ProjectArtDirection | 可复用的造型、画法、材质、光色与二维三维融合语言，以及冲突时的美术取舍 | 具体场景的必备建筑、左右构图、人物服装 |
| SceneDesign | 一个完整主方案的视觉关系、空间、主要物件造型、材质分布与探索回报 | 生图文件、网格拆分、UV、引擎节点与材质代码 |
| VisualProductionPlan | 用哪些视点、近看和分镜解决设计问题，及什么范围可继续探索 | 静默重写主方案或把图像偏差当成选定设计 |
| 后续资产制作契约 | 将选定设计交给模型、贴图、二维人物和引擎制作 | 代替上游重新决定场景主形象 |

仍是三组当前核心契约，第四组只保留制作职责。本轮不增加 DreamLoopSchema、审核评分树或通用资产装配系统。

Schema 的版本与美术预设内容版本分开。本稿没有改变当前项目选用的 `jiangcheng_retro_electric_noir@v0.2`。现有静态与移动实例仍保留各自原版本，不自动迁移。

## 1. ProjectArtDirection：增加可解释的美术取舍

保留 `intent / linework / values / surfaces / hybrid / scene_freedom / avoid / references`。

在现有 `intent` 中增加 `priorities: text[]`：按重要性说明制作发生冲突时，哪些表现应优先保留，以及哪些细节可简化。不是数值权重或自动通过条件，也不能覆盖无文字等明确约束。

本项目的填写示例，待讨论采纳：

- 优先保留人物与环境一致的漫画概括，以及有重量的建筑轮廓；微观磨损可以减少。
- 保留集中暖亮区与大片冷暗面的层次；反光可以减少，不能变成遮住石面的大块亮漆。
- 保留材质的不同画法：石面宽、木纹有方向、金属接缝克制；不能为统一风格把它们处理成同一种噪点。

不同项目自行填写这些优先关系；不把上述内容写成通用枚举。

## 2. SceneDesign：以关系和造型承载吸引力

保留顶层 `art_direction / intent / scope / art / space / elements / dressing / initial_state / experience`，在同一 SceneDesign 内增加 `visual_groups` 承载已确认的视觉组合。它不成为独立契约或独立调用阶段。
已有 `routes / motion / progression / encounters / handoffs` 继续按需使用。当前新码头增加拳击互搏设计；航行、远程武器和完整任务链没有因此自动纳入。

### 2.1 美术主张必须落到关系上

`intent.signature` 描述这个场景最有识别性的整体形象。`feeling` 和 `invitation` 继续描述感受、可见线索与接近欲望。

将现有 `space.relations: text[]` 改为 `VisualRelation[]`：

```text
VisualRelation
  id
  subjects: {zone_ids[], group_ids[], element_ids[]}
  arrangement: text
  visual_effect: text
  importance: text
```

- `subjects` 引用参与关系的已有区域和物件，不只列“能看见”的对象。
- `arrangement` 写高低、前后、尺度、遮挡、包围、连接或疏密的具体安排。
- `visual_effect` 写该安排让玩家实际看到或感受到什么。
- `importance` 写这组关系对本场景的作用，及允许调整的部分；不把所有内容都称作首要。
- 关系不能创造第二套物件位置。`placement` 给物件定位，关系说明它与其他对象一起构成什么；修改时一并保持一致。
- 关系可在一个画面中呈现，也可通过接近、转角或航行逐步显露；不强求全部塞进一个主镜头。

码头填写示例（实例提案，不是通用必备布局）：

```json
{
  "id": "working_bank_above_landing",
  "subjects": {
    "zone_ids": ["upper", "lower"],
    "element_ids": ["warehouse_shell", "stairs", "courier", "barge"]
  },
  "arrangement": "上层工作廊靠建筑，下层窄码头靠水；石阶斜向连接二者，人物站在下层转折处，船舷比人物脚下平台略低。沿入口看去，近岸墙局部遮住下层道路，船棚露在其外侧。",
  "visual_effect": "先感到岸线有层层下降的厚度；走下石阶后，人物与船体展开，上层廊下生活仍可回望。",
  "importance": "这是本场景的首要空间形象；阶梯具体级数可调整，不能将上下两层压成一块空平台。"
}
```

湿地填写同一结构时，可设计“近处低船舷—两侧高草岸—前方低桥洞”的包围与显露，引用 barge、bridge_a 和已有水道区域。这里没有 harbor、stairs 或 bridge 这种固定字段。

### 2.2 整体美术与关系各有职责

`art.composition` 保留 `massing / silhouette / depth / detail_distribution`，用于整体画面秩序；不要再次逐条抄写 relations。

`art.palette / lighting / materials / atmosphere` 保留：

- 色彩的 `role / placement` 指向真正需要它的位置，不只给色值。
- 光源的 `reach / visual_effect` 写明要连起哪些表面、人物或空间，以及哪里保留暗面。
- 材质定义共享画法，物件 `surface_uses.local_treatment` 表达该处的方向、密度、干湿及使用痕迹；无特殊处理可明确沿用，不编造差异。
- 氛围手段服务具体部位的运动与深度，不把雨、雾、蒸汽全部设为必备。

### 2.3 主要视觉物件要展开到造型决定

`VisualElement` 原有 `placement / visual_role / surface_uses / representation / integration` 保留。

`form` 调整为：

```text
form
  silhouette: text
  proportions: text
  parts[]
    name: text
    shape: text
    placement: text
```

`parts` 从部件名称串改为少量决定外观的部件说明。不逐颗螺栓枚举，不要求全部部件都独立成为资产。

- `silhouette` 写区别于同类物件的外轮廓、实虚关系与局部强调。
- `proportions` 只写这个对象自身的关键比例及必要的外部尺度参照。不能对五种物件重复同一段全场尺寸。
- `parts[].shape` 给部件自己的体量、转折、厚薄或开口安排，`placement` 给它与整体的相对位置。
- 若部件已独立定义为 element，相关文字引用该 element ID，不重新定义其外形；暂不建立递归装配结构。

例如船舱不能只写“船壳、甲板、船舱、窗、篷顶”。需要决定船舱占船长多少、船首留多长甲板、棚顶与护舷怎样错开、舱门从哪个方向可看进去。

`integration` 也必须对应对象：船写吃水线、系缆和甲板高度；壁挂设备写离墙间隙、挂点和管线去向；人物写脚底接触、头肩后方背景与可观察方向。保持设计意图，不在此写 billboard 或着色器实现参数。

### 2.3.1 已确认：先组合，后重点单件

视觉组合描述若干物件共同形成的外观；主要视觉物件描述其中值得单独展开的对象。两者都嵌套在 SceneDesign，不把组合伪装成一个物理实体。

```text
visual_groups[]
  id, name
  members: {element_ids[], dressing_ids[]}
  form: {silhouette, proportions, layering}
  visual_effect: text
```

- `members` 引用 elements 和 dressing 中已有内容。普通陈设继续按组记录，避免为每个木箱单建 Element。
- 组合 `silhouette` 写整体轮廓，`proportions` 写成员间体量比例，`layering` 写进退、开口、遮挡、色块和细节的整体组织。成员自身的部件造型仍只写在 elements。
- 成员的真实位置以各自 placement/arrangement 为准，组合不维护第二份坐标。组合层次或比例发生变化时同步修订相关成员。
- 同一物件可参与不同观察关系，仍只定义一次。组合只引用物件和成组陈设，不递归包含其他组合。
- 组合不等于 Zone：一个上层区域可以有两个组合，一个组合也可以跨门内外或岸船两侧。
- 组合不承担碰撞、整体运动或模型导出。移动成员仍读取自己的 motion；组合引用不会让所有成员自动一起移动。
- 单一对象就足以承担主形象时，直接设计该 Element，无需强建只有一个成员的组合。

SceneDesign 的设计顺序为：整体形象与空间关系 → 视觉组合的总体安排 → 重点单件的造型与表面 → 靠近和穿越时的视觉变化。最终 Structured Output 仍是一份内部一致的 SceneDesign。

### 2.3.2 两段对照走读：组合字段是否有用

以下为设计填写片段，引用旧实例中的 ID 便于对照，不是完整场景、已选新布局或已实现内容。`form.parts` 在完整实例迁移时另行展开。

```json

  "name": "仓门工作区",
  "members": {
    "element_ids": ["warehouse_shell", "shore_power", "courier"],
    "dressing_ids": ["crates"]
  },
  "form": {
    "silhouette": "厚门洞向内退，低雨棚向外挑；一侧窄高设备和弯曲电缆打破梁柱的直线节奏。",
    "proportions": "门洞足够看见人物身后的一段室内，雨棚横向覆盖门口工作面；设备保持人可操作的尺度，不压过入口；货箱低于人物肩线。",

  },
  "visual_effect": "远处先读出一个有深度的暖亮工作口，靠近后才分辨设备曲线、人物姿态和门内货物；没有单个杂物抢走整体。"

```

这里由组合决定入口、人物、设备和货物怎样共同成立；岸电箱的圆肩、把手、陶瓷节和挂墙间隙仍在 shore_power 中设计。跨越上层工作区与下层泊船的高差由 space.relations 组织，不塞进岸电箱的造型字段。

#### 移动湿地：船首灯与近岸桥洞

```json
{
  "id": "bow_and_bridge",
  "name": "船首与低桥的接近画面",
  "members": {
    "element_ids": ["barge", "bridge_a"],
    "dressing_ids": []
  },
  "form": {
    "silhouette": "近处低平船舷与前方宽低石拱对照，船灯只占一小块暖亮。",
    "proportions": "船首作为稳定的近景尺度；接近时桥洞逐渐包围前方视野，保留站立通过的净空。",
    "layering": "甲板在近处，两侧草岸夹住中段水路，桥洞在前方；穿桥时桥腹从头顶压过，洞外较亮的水面逐渐展开。"
  },
  "visual_effect": "船上视点连续经历开阔、收紧和重新显露，吸引力来自形体相对运动，不依赖战斗。"

```

桥仍为固定物件，船沿路线移动；二者属于同一视觉组合，不代表桥被绑在船上。组合描述接近过程的整体意图，具体时刻由 experience.situation 定位，View 决定船上或岸上的观察位置。

这两段说明组合可以承载静态整体或移动中的形体关系；还不能证明图像和行走体验已经成立。

### 2.4 体验必须有形象变化

### 2.4.1 人物表演与战斗能力的边界

在 `scope` 中增加按需 `player_view: {perspective, body_presentation, attention_rules}`，承载本场景游玩时的观察与身体呈现意图。当前实例填第一人称、画面下缘手与前臂、中心保留对手和通路的读图空间。它不自动改变通用 Schema 允许的其他视角，也不要求独立人物设定图使用第一人称。

为需要动作设计的 VisualElement 增加按需 `performance`；静态建筑等可省略，不按所有物件强制填空。

```text
performance
  everyday: text
  actions[]
    name: text
    preparation: text
    key_pose: text
    recovery: text
  reactions: text
  view_readability: text
```

- `everyday` 写待机、观察或劳动中的姿态特点，决定没有战斗时的人物生活感。
- `actions` 写需要表现的动作及其预备、关键形态和恢复。拳击可以使用抬手戒备、直拳、格挡等动作；不是所有角色默认敌对或所有场景必须有拳击。
- `reactions` 写受击、失衡或停止对打时如何反馈，让动作产生可见结果。
- `view_readability` 写不同观察方向下拳、头肩和躯干如何分离，哪些轮廓不能被袖口、包带或背景吞没。
- `motion` 继续负责对象在世界里怎样移动；`performance` 负责动作的视觉表现。两者不互相替代。
- 对打参与者、触发及结束的场景意图放在 experience/encounters；伤害、命中、AI、输入、无敌时间等留给玩法实现。动作帧数量、图集和朝向切换留给资产制作。
- 玩家第一人称拳头、对手二维动作和命中反馈是互搏呈现的三项不同制作内容；一張站姿图或举拳设定图不能代表已经能对打。
- 主角的外观、身份不从六名 NPC 的设定中自动指定。第一人称手部先按共享漫画画法设计，具体袖口等内容在相应资产草案中注明。

当前人物设计与实际生图见[六人首轮设计](harbor/characters-v0.3.md)，其造型与动作细节是提案。拳击范围已获得用户授权，无需再次询问是否允许加入战斗。

### 2.4.2 体验时刻

`ExperienceMoment` 保留 `cue / action / visual_payoff / capability_note`，增加按需 `relation_ids[]`，指向该时刻显露的视觉关系。

“走近后看清更多细节”可以作为说明，但不能替代具体回报。需写清原先被什么遮住，接近或转向后出现哪个形体、空间或材质交接。

移动场景仍使用 v0.2 的路线与时刻快照。关系本身描述共同设计，某时刻的位置和可见状态由 `situation` 表达，不复制一份事件流程。

## 3. VisualProductionPlan：围绕设计问题出图

保留 `scene_design / exploration / views / variants / scene_views / object_studies / storyboards`。

### 图像用途

在每个交付的共同字段中增加 `purpose`，取值：

- `design_exploration`：研究造型、构图或近看表现；允许变化范围由 exploration/variant 指定。
- `implementation_target`：已选择设计的实现参照；固定当前设计及视点，供运行画面对照。

三种图像交付类型仍负责“画什么”；purpose 负责“本轮用它作什么决定”。purpose 不等于批准状态，模型不能靠填写此字段把未选设计说成已选。

派生自白盒或小样的图可以辅助保持空间一致，但若锁定了未经选择的简化体块，不能直接当成新的美术标准。布局和造型尚在探索时，保留设计变化余地，并将选定变化回写 SceneDesign。

### 每个 View 回答不同问题

- `subjects` 增加按需 `relation_ids[]`。原有区域和物件列表按该画面实际要表现的内容筛选。
- `subjects` 同时允许 `group_ids[]` 引用视觉组合。引用组合不强迫显示其所有成员；实际取景、遮挡与当前时刻仍决定可见范围。
- `emphasis` 写一个具体判断问题，例如“岸墙遮住多少下层路径，才能让下降后的人物与船体产生展开感”。
- `composition` 说明前景遮挡、中景焦点和远景的安排。`camera.framing` 仅说明取景范围，避免重复写一段相同文字。
- `camera` 保留概念站位；实现目标增加按需 `fov_degrees / aspect_ratio`，不把镜头参数塞进 position 字符串。位置在移动实例中仍按 anchor 解释。
- 游玩视角与体验分镜沿用 `scope.player_view`；独立人物或物件研究视点应在 camera 中明确说明用途。不能把用于展示的第三人称镜头当成第一人称玩法已经成立的证据。
- `variants` 继续表达明确的局部设计差异；完全不同的主布局另建 SceneDesign。图像偶然变化不自动成为 Variant。

码头可以安排：到达图研究错层岸线与人物尺度；门内图研究门框裁切江面；下层回望研究建筑进退与上层生活；设备近看研究科技造型与材质交接。并非每张图都填写“漫画形体、材质与人物融合”。

### 分镜与近看

Storyboard 的 Frame 继续引用 View，`player_action / visual_change` 描述接近、转向和穿越后的具体变化。运行截图可以记录执行结果，但不能代替尚未开展的设计探索。

ObjectStudy 继续绑定 element 和 View。当主要物件的独特造型无法从全景中看清时，应安排该物件的近看研究；普通物件不强制逐件出图。数量由尚未解决的设计问题决定。

组合的整体近看可以使用 SceneView + 指向该组合的 View；ObjectStudy 专门展开重点单件，不另增第四类图像交付。

## 4. 后续制作交接：本轮只明确必要输入

制作阶段应取得一致版本的 SceneDesign、项目美术预设、选定图像及其学习范围。执行记录关联实际模型、贴图、人物图和运行截图，不让模型预先编造文件或通过状态。

后续资产契约需要承载：源物件/材质引用、选定外观、必须保留的形体与表面特征、预期观察距离与方向、模型/贴图/二维元素的制作分工、接触与受光要求。设计粒度现已确认；制作拆分按实际资源决定，一份视觉组合可以对应多个模型、贴图和人物图。先用岸电箱展开制作要求，并保留它在仓门工作区中的尺度与受光上下文，不先建立完整资产管理系统。

dream-loop 用于追近选定设计。若要改主要空间关系或主物件造型，回到 SceneDesign 与视觉探索；它的相似度评分不能代替对场景吸引力的判断。

首份人物制作交接草案见[第一人称互搏](harbor/first-person-brawling-v0.3.md)：将主角手部、NPC 动作与环境中的交互反馈分别列为资源职责，注明当前已有参考和缺失图像。它是后续资产契约的具体填写起点，尚非冻结的可执行资产 Schema。
